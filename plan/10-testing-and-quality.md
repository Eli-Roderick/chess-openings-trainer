# 10. Testing, performance verification and quality gates

## 1. Test layers

| Layer | Where | Runs in CI | Target |
|---|---|---|---|
| Pure logic unit tests | `packages/chess_core/test`, `packages/uci_engine/test` | yes | ≥ 90 % line coverage of `chess_core` |
| Engine integration | `packages/uci_engine/test` tagged `engine` | yes (Linux binary) | all engine jobs against real Stockfish |
| App unit + widget tests | `test/` | yes | every controller; every screen renders its states (loading, empty, data, error) |
| Integration (end to end) | `integration_test/` on Linux desktop | yes (`xvfb-run`) | the flows in §3 |
| Device checks | Eli's phone and Windows PC | no | phase checklists in each phase file |

Rules:
- Logic tests use seeded `Rng` and a fake `Clock`. No test depends on wall time or real randomness.
- Widget tests use `ProviderScope(overrides: ...)` with in-memory drift (`NativeDatabase.memory()`) and `FakeEngineService`.
- No network in any test. Drive transport is tested against an in-memory `FakeDriveTransport` that mimics list/create/update/download with md5.
- Golden tests are not used (fragile across platforms) except optional ones for the board theme preview, generated on Linux only.

## 3. End-to-end flows (integration_test, Linux)

Each test boots the real app with overrides: temp DB file, fake clock, seeded Rng, real Stockfish (engine-tagged tests) or fake engine.
1. **First run → demo → drill**: install demo, open, Train Random, play a full line correctly by simulating moves through the board's test API, end bar appears, auto-advances, stats show 100 % for that line, streak shows 1.
2. **Retry mode mistake**: wrong move animates back, retry correct, run accuracy reflects 0 for that ply.
3. **Restart mode mistake**: board resets to start, already graded ply keeps its grade.
4. **Comparable move** (real engine): play a known comparable alternative; banner text appears; grade 0.5 persisted.
5. **Hints**: level 1 highlight, level 2 arrow, grade 0.
6. **Branch start**: start position equals branch ply; skipped chip visible.
7. **Alternative repertoire move** (Black fixture with a user fork): line switches, run stored under the completed line.
8. **Weak pool**: script runs to push a line under 80 %, Weak mode picks only it, 3 clean runs remove it.
9. **SRS**: new line introduced, pass → due tomorrow; advance fake clock; due again; fail → relearn same day.
10. **Import report**: malformed fixture shows warnings grouped; Import enabled; error fixture disables Import.
11. **Re-import**: v1 → train → v2 diff counts correct; extended line keeps accuracy; removed line archived.
12. **Browse**: navigate forward through a fork chooser; comment panel content; free exploration and back.
13. **Analysis** (real engine): toggle on, eval bar updates, toggle off stops engine (no info lines afterwards).
14. **Deviation** (real engine, chance 100 %): default timing plays the whole line from the book, then the opponent plays off-book, banner, reply judged, Play on opens; the run counts as a normal run in stats.
15. **Backup round trip**: export, wipe, import (merge), identical stats.
16. **Sync** (fake Drive): two app instances (two DBs, two deviceIds) sync through the same fake Drive; both converge to identical runs and repertoires; rename conflict resolved by newest.

## 4. Static quality gates (CI, every PR)

`dart format --set-exit-if-changed`, `flutter analyze --fatal-infos` (very_good_analysis), all tests, generated code up to date, import-boundary test (chess_core/uci_engine import no Flutter/app code; features don't import other features except `features/board`), no `print(` in lib (test greps), no `TODO` without `#issue`.

## 5. Performance targets and how each is verified

| Target | Automated proxy (CI, Linux) | On-device verification (Eli, Diagnostics screen) |
|---|---|---|
| Cold start < 1.5 s to usable Home | integration test asserts Home data visible < 1.5 s on CI (debug-free profile not available in CI, so this is a loose regression guard only) | Diagnostics "Startup": `main()` → first frame and → Home data ready, measured with `Stopwatch` started at the top of `main` plus the Android process start time from `Process.myProcess` start (via the `rt/native` channel `processStartElapsedMs`). Release build. Target total < 1500 ms. |
| No dropped frames on the board | none reliable in CI | Diagnostics "Frames": `SchedulerBinding.addTimingsCallback` collects `FrameTiming` since last reset; shows frame count, % over budget (budget from display refresh rate), worst build and raster ms. Eli resets, drills 5 lines, reads. Target < 1 % over budget, worst raster < 2× budget. |
| Opponent reply ≤ 300 ms after the user's move | widget test with fake clock asserts the opponent move is dispatched at `delay` after the drop | Diagnostics "Drill latency": p50/p95 of (user move drop → opponent animation start) over the session. Target p95 ≤ 300 ms at default settings. |
| 1,000-line import < 2 s on phone | `tool/bench_import.dart` in CI: 1,000-line synthetic PGN (depth 16) parse+build+validate < 1.0 s on the CI runner | Import report footer shows "Processed in N ms"; Eli imports the synthetic file (Diagnostics → "Import benchmark" generates and imports it into a temporary repertoire, then deletes it). Target < 2000 ms. |
| Stats derivation | 50k synthetic runs derive < 1 s in CI | Diagnostics shows last derivation time. |

## 6. Diagnostics screen (hidden; About → tap version 7 times)

Sections: Startup timings; Frames (with Reset); Drill latency; Engine (binary path, variant, version string from `id name`, threads, hash, calibration nps and depth-at-1s, last 20 job durations); Import benchmark button; Database (file size, row counts per table, last derivation ms); Sync (deviceId, last results, remote file list); Logs (Export logs → zip of log files via save dialog). Built in P04 (startup and frames), extended in P06, P07, P12, P13.

## 7. Manual device checklists

Each phase file ends with a short checklist for Eli on Android (and Windows where relevant). The build thread posts it with the PR; a phase is complete when CI is green and Eli has ticked the checklist (or waived it).

## 8. Review checklist for each PR (for reviewing agents)

- Matches the phase file's acceptance criteria item by item.
- No logic in widgets; providers scoped correctly; no unbounded rebuilds of the board (check with `debugPrintRebuildDirtyWidgets` in a widget test or by review).
- All user strings in ARB.
- Errors handled and shown (no silent catches without logging).
- Async work cancelled on dispose (engine streams, timers, animations).
- DB writes in transactions; long work in isolates.
- Tests cover the edge cases listed in the spec section.
