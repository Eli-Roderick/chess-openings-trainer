# P06 corrections (from the P06 build thread, 2026-10-06)

1. **Where judgements happen.** 05 §4 lists `checkComparable`, `deviationCandidates` and `judgeReply` on `EngineService`, while P06 task 1 asks to keep `uci_engine` chess-agnostic. `uci_engine`'s `EngineService` returns raw engine scores (`EngineScore`: cp or mate, side to move) and UCI lines (`scoreMoves`, `bestLine`, `topLines`, `analyse`, `playMove`, `calibrate`); the app's `EngineJudge` (`lib/core/engine/engine_judge.dart`) turns them into `ComparableOutcome`, deviation candidates and `ReplyJudgement` with chess_core's existing 04 §7 functions, so that maths has one implementation. (D-78)
2. **Results by move, not by MultiPV slot.** Keeping the last `info` per MultiPV slot gave duplicate or missing moves: a stopped search can leave a slot holding a line from an older depth whose move has since moved to another slot (seen on the real binary). Restricted searches are scored by each move's deepest exact line; top lines come from the deepest iteration that reported every slot. (D-79)
3. **Comparable-check test pairs.** The 05 §10 example (after 1.e4 e5 2.Nf3, book 2...Nc6: 2...Nf6 comparable, 2...f6 not, at 30 cp) is too close on sf_18: 2...Nf6 measured 1-17 cp worse than 2...Nc6 at depth 12-16 across runs, against a 30 cp threshold. The engine tests assert pairs with wide margins: 2...f6 loses more than twice the threshold (measured 93-166 cp, also under CPU load); two knight moves in a dead-drawn K+N v K position both score exactly 0; Scholar's mate scores as mate 1. The Nc6/Nf6/f6 numbers are logged on every run.
4. **Analysis lines setting.** 01 §9 has "number of lines setting 1-3 (default 1)" but 01 §10 has no such setting. Added `AppSettings.analysisLines` (1-3, default 1), changed from the 1/2/3 control in the analysis panel.
5. **Calibration storage.** Calibration results are device-local data, not a user setting: stored as JSON under `engine.calibration` in the `sync_state` key/value table. The automatic run starts after 10 s with Home on top (`ModalRoute.isCurrent`); if a screen covers Home when the delay ends, it waits another 10 s. (D-82)
6. **"No info lines received afterwards within 1 s".** Lines already in the pipe when `stop` is sent are allowed for 200 ms; the integration test then expects no `info` line for the rest of the second.
7. **Analysis must not rebuild Browse.** Updating Browse with `setState` 10 times a second, an `InkWell` per move in the move list and a panel whose height changed with every update rebuilt and re-laid out the whole move list on each navigation: 4-14 frames per 30 s over the 16.7 ms build budget in profile mode with analysis running (mean build 5.0 ms). Now: updates go through a `ValueNotifier` that only the eval bar and lines listen to, the panel has a constant height for its line count, moves are a plain `GestureDetector`, and move-list lines are cached so a navigation rebuilds only the two lines whose selection changed. Measured: 0 slow builds, worst 11.8-14.5 ms, mean 2.0 ms. (D-83)
